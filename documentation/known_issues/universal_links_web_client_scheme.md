## Diagnosis

The customer's `SchildiChat.js` iOS branch (line 99) returns a **custom URL scheme**:

```javascript
case Platform.iOS:
    // Используем основную схему приложения с фрагментом #/
    return `org.ucmeet.UCMeetChat://#/${fragmentPath}`;
```

Element's reference (`Element.js` line 83-90) returns an **HTTPS Universal Link**:

```javascript
if (isWebPlatform || platform === Platform.iOS) {
    let instanceHost = trustedWebInstances[0];  // "app.element.io"
    return `https://${instanceHost}/#/${fragmentPath}`;
}
```

The difference is the entire bug.

| Link form generated by web client | What happens when shared via Telegram / Mail / WhatsApp |
|---|---|
| `https://ucmatrix.org/#/<fragment>` | All messengers render it as a tappable link. Tap → iOS reads AASA → opens UCMeet.Chat directly to the right screen. **✅ Works.** |
| `org.ucmeet.UCMeetChat://#/<fragment>` | Most messengers refuse to render it as tappable at all (custom schemes look like attack vectors to them). Even when tappable, iOS does not route custom schemes via AASA — they only resolve when invoked from another app that knows the exact scheme. **❌ Dead on arrival.** |

This is why:

- **My 2026-05-13 E2E test passed.** I hand-typed `https://ucmatrix.org/#/!realRoom:matrix.ucmeet.org` into a Telegram message and tapped it — that's the HTTPS form, so it worked.
- **The customer's flow fails.** When a user in the web client at `ucmatrix.org` clicks "Share room → Copy link", the JS in `SchildiChat.js` builds the `org.ucmeet.UCMeetChat://#/…` form. They paste that into Telegram. Telegram won't even underline it.

## Fix

Customer-side, one line in their web client codebase:

```diff
 case Platform.iOS:
-    // Используем основную схему приложения с фрагментом #/
-    return `org.ucmeet.UCMeetChat://#/${fragmentPath}`;
+    // HTTPS Universal Link — iOS intercepts via AASA and opens UCMeet.Chat.
+    // Custom URL scheme is intentionally NOT used: messengers strip it.
+    return `https://ucmatrix.org/#/${fragmentPath}`;
```

`fragmentPath` already builds the right shapes for every link kind (user / room ID / room alias `%23` / event / `?via=` params) — that part of `SchildiChat.js` is correct. Only the scheme + host need to change.

No iOS code change. Once `SchildiChat.js` is redeployed on `ucmatrix.org`, the existing TestFlight 1.0.2 build 1 will work end-to-end.

---

## Why we explicitly do NOT add a custom-scheme parser in the iOS app

It would be a 30-line addition (mirror `UCMatrixPermalinkParser` but match `url.scheme == "org.ucmeet.UCMeetChat"` and `url.host == nil`). But:

1. It would not fix the customer's actual complaint. Telegram / Mail / WhatsApp **strip custom schemes before display**, so the link is unclickable regardless of what our app supports.
2. It would create a parallel, inconsistent code path that future syncs would forget about.
3. The Element reference (`Element.js`) demonstrates the industry pattern: HTTPS Universal Link, period. Following it keeps us aligned for future upstream syncs.

Decision recorded against option 1 of plan `so-we-have-recently-crispy-floyd.md` (2026-05-20).

## Escalation path (if step 4 above fails after fix)

Unlikely given the 2026-05-13 verification, but if it does fail:

1. **Re-verify AASA** — `curl -v https://ucmatrix.org/.well-known/apple-app-site-association` and inspect `Content-Type`. Must be `application/json`, not `application/octet-stream` or `text/plain`. Apple's `swcd` daemon rejects the wrong Content-Type.
2. **Force iOS to re-fetch AASA** — delete and reinstall UCMeet.Chat from TestFlight. iOS caches AASA for 24h after install; reinstall forces a fresh fetch.
3. **Capture `swcd` logs on device:**
   ```bash
   xcrun simctl spawn booted log show --predicate 'subsystem == "com.apple.swcd"' --last 5m
   ```
   (Simulator only — on real device, use Console.app filtered by `swcd` while reinstalling.)
4. **Validator** — paste the AASA URL into <https://branch.io/resources/aasa-validator/> (or `swiftc -emit-imported-modules` is not relevant here — use the web validator).
